# IndustryForms — repo-wide rules

Cross-cutting rules only. Per-app rules live in `tradiee-app/AGENTS.md` and
`tradiee-mobile/AGENTS.md` (both load automatically when you touch files in
those directories). Narrative history and open action items live in
`PROJECT_STATE.md` — read that for *what's going on*, this for *what not to
break*.

## Layout

- `tradiee-app/` — Next.js web app + all API routes. Mobile calls these too.
- `tradiee-mobile/` — Expo app, offline-first via PowerSync.
- `supabase/migrations/` — schema. `sync-rules.yaml` (repo root) — PowerSync.
- Repo root is also the marketing static site (`index.html`, `blog/`,
  `trades/`, `alternatives/`), generated by `scripts/build-*.mjs`. There is no
  root `package.json` and no build step — generator output is committed.

## PowerSync: the trap that has already caused one outage

Adding a table to `sync-rules.yaml` is **never** enough on its own.

1. The table must also be in the `powersync` **Postgres publication**. This is
   database-level state that `supabase db push` does not recreate.
2. **Logical replication does not backfill.** Adding a table to a publication
   streams only *future* changes, so PowerSync holds an empty copy and JOINs
   against it silently match nothing. Same for `ALTER TABLE ADD COLUMN` — the
   new column never reaches already-synced rows. Force existing rows through
   the WAL with a no-op `update <table> set id = id` in the migration.
3. The table must be added to the PowerSync client schema in **both**
   `tradiee-app/lib/powersync/schema.ts` and
   `tradiee-mobile/lib/powersync/schema.ts`.

Run `node scripts/check-sync-rules.mjs` (from repo root) after any
`sync-rules.yaml` edit. It asserts every query is `auth.user_id()`-scoped,
role-gated where required, and that every referenced table is actually
published.

Prefer reusing an already-synced table over adding a new one — it skips all of
the above. See `JOB_MESSAGING_SCOPE.md` for a worked example.

Mobile queries reading a newly-added column must tolerate `NULL` for it: a
device can sit offline for days holding pre-migration rows.

## Multi-tenancy

RLS is the tenancy boundary, not application-layer checks. Every new table
needs `company_id`, RLS enabled, and policies scoped to `current_company_id()`
with writes limited to owner/admin. Public/unauthenticated access goes through
a server route using the service client, never by loosening RLS.

A route using the **service client bypasses RLS entirely** — re-check the
equivalent predicate by hand there.

## Migrations

- Applied to production with `supabase db push --linked`. That's a deliberate
  human action; don't run it as a side effect of something else.
- If a migration changes what a column *means*, land the read-side filter in
  the **same commit**. A window where the column exists but readers are
  unfiltered is how wrong data reaches a customer-visible document.
- Money is `numeric`, never float. supabase-js returns `numeric` as a
  **string** — `Number()`-coerce or `"125" + "300"` silently concatenates.

## Checks instead of a test framework

Non-trivial logic leaves one runnable `scripts/check-*.mjs` behind — plain
`node`, `assert`-based, no framework. Existing ones:

- `node scripts/check-sync-rules.mjs` (repo root)
- `node scripts/check-job-financials.mjs`, `check-invoice-guard.mjs`,
  `check-statement.mjs`, `check-job-thread-recipients.mjs`, `check-xero.mjs`
  (from `tradiee-app/`)
- `node scripts/check-invoice-numbering.mjs` — needs local Supabase running,
  unlike the pure-JS ones above
- `node scripts/check-map-escaping.mjs` (from `tradiee-mobile/`)

## Before saying it works

- `npx tsc --noEmit` in **both** apps. Mobile has no eslint config — `tsc` is
  its only static gate; web additionally runs `npx eslint`.
- After adding or deleting an API route, `tsc` may report phantom errors for
  the old path from a stale manifest. `rm -rf .next/types .next/dev/types` and
  re-run before believing them. Dev-server API 404s have the same cause —
  restart the dev server rather than debugging the route.
- `tsc` and `eslint` passing is not "verified". Say plainly which parts were
  exercised against real data and which weren't; this repo has a history of
  live testing catching what static checks could not.

## Secrets

Never commit `.env.local` or hardcode keys in `scripts/` — GitHub secret
scanning has blocked a push here before over a service-role key in a check
script. Read credentials from the environment.
